# 技术之外的支配项 —— 许可、成长与记忆

聊起 LLM，我们的注意力总会不由自主地被"聪明"或"快"这类技术指标吸引。然而 2026 年上半年，从家用 CPU 这个视角观察整个行业，我反复领悟到的却是另一件事。**左右一款产品命运的，往往并非技术本身，而是处于技术"外侧"的支配项** —— 就是这件事。

所谓支配项（dominant term），指的是对结果影响最大的那一项。把性能翻一倍，可商用许可不合适也无法采用。把学习循环提速，可若没有阻止错误的机制，就会"越用越退化"。把记忆机构打磨得再精，可一旦弄错了"在哪个领域畳什么"，也得不到一致性。本文（连载《从家用 CPU 看 2026 年 6 月的 LLM 行业》生态系统篇）将沿着 **许可 → 成长 → 记忆** 三段，巡视这些"技术之外的支配项"。

---

> ### 通用免责声明（适用于本连载全篇的横幅）
>
> 本连载核心（llcore）所给出的**实测值，全部是家用 CPU 上极小模型 PoC 的 honest disclosure**。这并不是要直接反驳或超越大厂的真实 LLM。本文中会出现与大厂、其他公司、其他项目作比较的场面，但比较的是**手法、思想、计量纪律这一维度**，而非绝对性能的优劣。并且本文**既不是法律建议，也不是投资建议**。对其他公司（Google / NVIDIA / Baidu / Nous Research / MangaFlow 作者等）的提及，全部基于公开信息在 2026 年 6 月时间点的理解，数值均附注出处。一如本连载的做法，**斩向他者的刃，最后必定也会指向自己（FullSense / llcore / llive）**。

本文中会多次出现的通用术语，在此统一定义一次（各章不再重复）。

- **honest disclosure（诚实披露）**：在主张"成功了"之前，先怀疑其内里的构成，不隐瞒未经证明的部分、前提条件与反例的纪律。它是本连载的脊梁。一旦出现异常漂亮的数字，在自以为获胜之前，必须先拆解。
- **OSI 认定 OSS**：满足 Open Source Initiative 定义（自由使用、改写、再分发，不歧视领域等）的许可。Apache 2.0 与 MIT 是代表。在自称"open model 许可"的东西里，有些**并不满足**这一点。
- **常数状态（constant state）**：无论读取多少过去，都将其畳进固定大小的"摘要"中携带的方式。即便文章变长，状态的大小也不增加，这是 recurrent / SSM 系的思路。第 3 章会详细处理。

# 第 1 章 —— open weights 的许可裂成了 3 种

## 仅凭"open"一词，无法确定能否商用

2026 年上半年，备受关注的 open 模型接连发布（Gemma 4 在 4 月，Cosmos 3 / PaddleOCR 在 6 月）。有意思的是，**许可裂成了 3 种**。如果用"open（公开权重）"一概而论，就会漏掉这层差异。

"open weights"只意味着"**权重可以下载**"而已。"能商用""能自由发布衍生物""属于 OSI 认定的经典 OSS"，则是**各自独立的事**。即便权重落得下来，也有的对商用使用附加条件，有的对衍生物设有限制。所以并非"是 open 就放心"，而是需要分辨**属于哪一种 open**。

### 租赁品的比方

即便是标着"免费出借"的工具，仔细看条件也各不相同。

- **A：真正自由**（改造、再分发、商用都 OK）
- **B：能借，但商用另有条件**（不读合同就不知道）
- **C：本体自由，但里面的零件归另一位出借方所有**（零件那一侧的条件也要确认）

只看"免费出借"的告示就以为全是 A，日后会犯难。AI 的公开，恰恰也是同样的情形。

## 裂成 3 种的实例（2026 年上半年）

把这一时期发布的 3 个，按许可这条轴排列。

| 模型 | 许可 | 种类 | 商用本地使用的判断 |
|---|---|---|---|
| **Gemma 4**（Google） | **Apache 2.0** | OSI 认定 OSS | 障壁为零（后述的"变更"意义重大） |
| **Cosmos 3**（NVIDIA） | **OpenMDW 1.1** | open model 许可（并非 OSI 认定的经典 OSS） | 需**逐条实读**商用条件、衍生物条款之后 |
| **PaddleOCR-VL**（Baidu） | **Apache 2.0**（但需注意基座） | OSI 认定 OSS | 虽是 Apache，但**需确认 ERNIE-4.5 基座的衍生许可** |

![一张将 2026 年上半年的 3 个模型按许可这条轴分派到 3 种（OSI 认定 OSS / open model / 自有条款·有条件）的地图。Gemma 4 为 Apache 2.0，Cosmos 3 为 OpenMDW 1.1（非 OSS = 需逐条实读），PaddleOCR-VL 虽为 Apache 但基于 ERNIE-4.5 需确认。要点是"权重能落下来（技术）与能商用（许可）是两道独立的验收"，采用前需把种类、商用条件、基座继承这 3 点分别确认的一张地图。](../../../assets/articles/llcore_c1_license_map.svg)

_把本章要点"即便是『免费公开』，条件也裂成 3 种"浓缩成一张的图。_

### (a) Gemma 4 = 向 Apache 2.0 的"变更"是货真价实的前进

Gemma 在 1/2/3 之前，一直以 Google 自有的 **Gemma Terms of Use** 分发。这一点在 Gemma 4 上**变成了 Apache 2.0**，意义重大。自有条款容易附带使用限制或再分发条件，而 Apache 2.0 是 OSI 认定的、直白的 OSS。**商用本地使用的障壁实质上变为零**。这不是"小版本更新"，在许可层面是**质的前进**。看似不起眼，却是让工作中使用的障壁几乎消失的一大步。

### (b) Cosmos 3 = OpenMDW 1.1 是"open 但并非 OSS"

NVIDIA 的 Cosmos 3 是 **OpenMDW 1.1**（Linux Foundation 系的以 model 为中心的许可）。它自称"open model"，但**与 OSI 认定的经典 OSS 是两回事**。商用条件和衍生物的处理，未必像 Apache 那样一律"自由"。**不读条文就判断"是 open 所以商用 OK"，是危险**的套路。对应到刚才那个租赁品的比方，就是"B：能借，但商用另有条件"。

### (c) PaddleOCR = Apache 2.0，但需注意基座

PaddleOCR-VL 是 Apache 2.0。看着直白，但**因为它基于 ERNIE-4.5**，所以需要确认基座模型那一侧的许可继承。"封装层是 Apache，但内核的继承另算"这种模式，是衍生模型中常见的陷阱。对应到租赁品的比方，就是"C：本体自由，但里面的零件归另一位出借方"。

## 为什么这关系到 FullSense / llmesh 的战略

从这里开始才是"那又如何"的正题。我所参与的 FullSense 采用 **Apache-2.0 + Commercial dual-license**，其中的 **llmesh** 是"把多个 LLM 在 on-prem（手边）整合并分发的枢纽"。对 llmesh 而言，**能在本地商用使用的后端模型增多**，就直接等于选项的扩大 = 顺风。

- **Apache 2.0 的可本地运行模型增多了**（Gemma 4 等）→ llmesh 的 on-prem 后端候选，得以毫无商用障壁地增多。
- 另一方面，**不过度依赖带有商用障壁的模型（自有条款·有条件的 open model 许可，或如 Qwen 系那样的商用条件）**，才是作为 dual-license 产品的安全侧。FullSense 正是从"依赖 Qwen 可能成为商用障壁"这一观点出发，重视后端的可搬性。

还有一点，它强化了 **llcore（自制极小模型研究）的定位**。在"Apache 2.0 的优秀本地模型增多了"的世界里，**用自制模型去比拼聪明的意义越来越淡**。需要对话品质的话，经由 llmesh 跑 Gemma 等即可。**llcore 不在模型层面竞争，而是彻底做内存效率的研究载具** —— 这张许可地图，从背面支撑了这一分工的正确性（这个押注"内存效率"的赌注，第 3 章会再回来）。

## 第 1 章的带走要点 —— 把"open"拆成 3 个问题

把公开模型纳入采用候选时，不要问"是不是 open"，而要把下面 3 点**分别**确认。

1. **许可的种类**：是 OSI 认定 OSS（Apache/MIT），还是自有条款，还是"open model"许可（OpenMDW 等）。
2. **商用使用的条件**：商用是否有附加条件·限制（营收阈值·用途限制·归属义务的范围）。
3. **衍生物与基座的继承**：能否发布衍生模型。是否继承了基座模型的许可。

> **检测信号**：不要凭"open weights！"一句就判断能否商用。确认许可名称，**只要不是 OSI 认定 OSS 就务必逐条实读条文**。即便写着"Apache"，也要往上追一层基座模型的继承。

### honest 的保留（第 1 章）

- 本章**不是法律建议**。许可分类是把握方向的地图，**具有约束力的是各模型许可条文本身**。在做采用判断之前请阅读原文。
- 所记内容是**2026 年 6 月时间点的理解**，许可可能被修订（正如 Gemma 在 3→4 时所做的变更）。
- 各模型的细节（OpenMDW 1.1 的商用条件·衍生物条款、ERNIE-4.5 基座的继承范围），本章**并未做到条文的逐条核对**。明确标注"需逐条实读"之处，正是采用前的确认要点。

许可是"技术之外的支配项"的第一个例子。性能再好，商用条件不合也无法采用 —— **把权重能落下来（技术）与能商用（许可），分别验收**。这就是把 honest disclosure 套用到许可层面的做法。下一章处理另一个"技术之外的支配项" —— 智能体的"成长"。

# 第 2 章 —— "成长"与"负责任地成长"是两回事

## "越用越长进"未必等于"变好"

如果说许可是"能否采用"的支配项，那么对自我成长智能体而言，支配项就是"**成长的方向**"。我们来解剖当下最火的口号——"自我成长的智能体"。

先把结论说在前面。**"越用越长进"是迷人的说法，但"长进"并不意味着"变好"。** 一旦囤积了错误的学习，智能体也可能"越用越退化"。本章用"负责任地成长"这一设计思想，重新审视这个分岔点。

## Hermes Agent 是什么（公平地，先从长处说起）

Nous Research 的 **Hermes Agent**（OSS，MIT 许可，**2026 年初发布**），是一款以 **built-in learning loop（内置学习循环）**为卖点的智能体。据公开信息，其骨架为以下 5 点：

1. 任务完成后**自动生成 skill（可复用的步骤）**
2. 使用过程中**自我改进 skill**
3. **将记忆持久化**
4. 通过 **FTS5 进行全文横向检索**回溯过去
5. 通过 **Honcho 进行 user modeling**（对用户画像的学习）

一款"越用越为你量身长进"的智能体。这是货真价实的魅力，GitHub star 也非常多（后述，但对 star 的质量有所保留）。而且，它与我所参与的 **llive**（标举自我进化·4 层记忆·派生群体进化的认知 OS），**正面竞争**。正因如此，我才要公平地、却也诚实地审视它。

## ★核心 —— "成长"有一个隐含的前提

"越用越长进"这一主张，有一个**未被言说的前提**。

> **所学的东西，未必总是正确的。**

当智能体"任务后自动生成 skill 并复用它"时，假如那个 skill **是错的**，会怎样？错误的步骤囤积进记忆，在下一个任务里被复用，进而成为另一个 skill 的地基。**错误自我增殖** —— 这一点我称之为"污染循环"（二次信息中也指出过同类风险）。

具体而言是这样的。设 AI 一旦记下"这类作业用这套步骤"，而这套步骤里有个小错误。那么在下一个相似作业里，那套错误步骤就会原样被调用，并在其之上又叠起"用了这套步骤的、更大的步骤"。这样一来，事后再把最初那个小错误抽出来就很难，AI 会连地基一起带着脏的状态"成长"起来。

打个比方，就像**带着一身自创的怪毛病继续练习的运动员**。越练就越厉害——未必如此。若反复练习错误的动作，**也可能越练越把烂功夫练定型**。一旦把"成长"无条件当作善，就看不见这个污染循环了。**成长 = 改善，并不成立。** 学习循环，学对了就改善，学错了就退化。它是朝两个方向都开着的刃。

![一张图，展示同一个内置学习循环（skill 自动生成/改进/记忆持久化/全文检索/user modeling）如何因有无门控而朝两个方向分岔。无门控（成长）通向错误自我增殖的"污染循环"，而咬合了承认门控（Approval Bus / HITL / honest disclosure, fail-closed）的"负责任地成长"则朝着不让错误 skill 默默通过、把它拦住的方向。右列展示 Hermes 与 llive 都没有独立基准·同行评审，两者皆未经证明。分岔点不在于"能学多少"，而在于"学错时能否拦住"，这是一张图。](../../../assets/articles/llcore_c2_responsible_growth.svg)

_即便是同一个学习循环，能否在 architecture 中具备拦阻机制，就决定了是"长进"还是"退化"。_

## 所以该问的不是"是否成长"，而是"是否负责任地成长"

llive 的设计思想分岔点就在这里。llive 比"成长"更进一步，把**"具备拦阻错误学习的机制而成长"**置于 core。具体机制为：

- **Approval Bus**：把状态变化（skill 的采用·向记忆的晋升）通过一道并非无条件放行、而是需要承认的关卡。
- **HITL（Human-in-the-Loop）**：在重要学习的取舍上，夹入人类（或更上位的验证）。
- **honest disclosure**：在主张"成长了"之前，先怀疑那份学习是否真的是改善，并披露其内里构成（就是本文开头定义的那条纪律）。

这些归根结底，是**"在学习循环上咬合一道 fail-closed 的门控"**的设计。所谓 fail-closed，是"拿不准就不放行、先拦住"的默认动作。说白了，就是把"有教练在旁边喊『那个动作错了』来拦住你"的机制，**从一开始就嵌进去**。不靠咬牙留神，而是**作为 architecture 来拦阻错误学习**。

> 成长的智能体 = 转动学习循环。
> 负责任地成长的智能体 = 在学习循环上咬合**承认门控**，拦住污染。

FullSense 的设计哲学（把责任所在带进 architecture level）在这里被具体化。

## ★这里把刃指向自己（不只斩竞争对手）

到这里为止，会被读成"llive 厉害 / Hermes 危险"。那正是本连载最厌恶的套路。要公平地，用同一把尺子去量两边。

**对 Hermes 一侧的公平评价：**

- Hermes 实实在在地存在，以 MIT 公开，被广泛使用，是货真价实的 OSS。断定它"危险"是不公允的。
- 不过 honest 地看，**展示 learning loop 有效性的独立基准·同行评审论文，目前无法确认**（arXiv 检索 0 件，效果主要是官方自称）。"长进就会变好"是**尚未经第三方验证的主张**。
- GitHub star 在 **数万规模**（多份独立报告称 2026 年 4 月时间点约 47,000～57,000，自 2026 年 2 月发布起两个月内的猛增），确实很有人气。不过 **star 的数值·质量（bot / 来自宣传活动的比例）因出处而互相矛盾**，我最初参照的"约 196,554"这个值在其他来源得不到佐证（有过大之嫌）。**"心智份额先行"的威胁确实存在，但规模的精确数值依赖出处，其确度需要保留**。
- 为避免夸大，也明确一点：就公开信息而言，最近的发布**偏向于在既有 core 上套 GUI 外壳**，并非新增模型·新框架。

**对 llive 一侧（自己）的同一把刃：**

- **llive 同样未经证明。** 展示 Approval Bus + HITL"实际拦住了污染循环"的独立基准，我还没有拿出来。"负责任的成长"在当前时点**是设计思想，而非已被实证的优势**。
- 既然对 Hermes 说"没有独立基准"，那同一张标签也会贴到 llive 身上。区别仅在于"**是否在 architecture 中具备拦阻污染的机制**"这一设计上的有无，而该机制的有效性，**两者都还有待今后验证**。
- 既然标举"成长 ≠ 改善"，那么 llive 自身的"进化"，也是不能自以为获胜、需要怀疑其内里构成的对象。

也就是说，诚实的结论不是"llive 更优秀"，而是**"两者都未经证明，但 llive 押注在『从一开始就把拦阻错误学习的机制嵌进 architecture』的那一侧"**这一设计选择的表态。

## 第 2 章的带走要点 —— 看到"自我成长"就问 3 件事

看到"越用越聪明的 AI"这句卖点，请确认下面 3 件事。

1. **谁来保证学习的正确性**：自动生成的 skill / 记忆，是否被无条件采用。是否有承认·验证的门控。
2. **是否有污染循环对策**：错误的学习囤积并被复用的路径，是否有拦阻它的机制。
3. **"长进就会变好"是否经过验证**：是有独立基准·同行评审，还是自称（这一条既问竞争对手，也问自己）。

> **检测信号**：若把"越用越聪明"当作无条件的善来谈，就要警惕。成长是双刃，**有无拦阻机制**是责任的分水岭。

### honest 的保留（第 2 章）

自我成长智能体的竞争，容易用"能学多少"来谈。但真正的分岔点是**"学错时，能否把它拦住"**。学习循环若没有承认门控，就会反转为污染循环。不过 —— 一如本连载的做法，最后再说一次 —— **该机制是否真的拦住了污染，llive 自身也还没有证明。** Hermes 与 llive，同处"未经证明"的台阶上。不同的只是所押注的设计。"负责任的成长"，是接下来要用实测去证明的**承诺**，而非已达成的胜利。

把责任放在"运营中留神"，而是**置于 architecture** —— 在这里，第 2 章出现的"将记忆持久化、事后回溯"这一共通机制，其实正是第 3 章的主角。Hermes 也好 llive 也好，都用着这副骨架。最后一章，我们来看那份"记忆"如何跨领域地重演。

# 第 3 章 —— 凭记忆获得的一致性，是跨领域的普遍部件

## "把过去畳进记忆，事后回溯"

第 2 章里，智能体具备了"将记忆持久化、事后回溯"的机制。其实"**把过去畳进记忆以保持一致性**"这一思路，并不止于 LLM 的长上下文或智能体，**在多模态生成（漫画生成）中也以同一副骨架奏效**。本章收集这方面的旁证。

这里请回想开头定义过的 **常数状态**。文本 AI 在处理长文时，无论读取多少过去，都将其畳进固定大小的"摘要（状态）"中携带。把当天的日记在当天就压缩成一张摘要卡，第二天只看卡片即可 —— 就是那个思路。recurrent / SSM 系正是用它，即便文章变长，状态的大小也不增加。

## MangaFlow 是什么（公平地，先说要点）

**MangaFlow**（东大 + 香港科技大广州，arXiv:2605.28173）是一项生成漫画的研究。漫画生成的难点之一，是**跨格的角色一致性**——同一个角色在下一格里被画得像换了个人就麻烦了。MangaFlow 用 **story section memory（故事章节记忆）**来担保这一点。

机制是，给各章节**绑定角色·场景·对象的引用，并在格与格之间复用的外部记忆**。把"这个角色长这样"的引用持有在记忆里，在后面的格中回溯取用。ablation（移除该机制的实验）显示出了其贡献（后述·self-report）。

## ★骨架相同 —— "把过去畳进记忆，事后回溯"

这里就与连载的主线接上了。MangaFlow 的 story section memory，从结构上看，与 **llcore / llive 反复采用的"凭记忆保持状态"的思路是同一副骨架**。

- **LLM 的长上下文**：常数状态 recurrent / SSM 把过去畳进固定大小的状态携带，用于后面的预测。
- **漫画生成**（MangaFlow）：把角色引用畳进外部记忆持有，在后面的格生成中回溯。
- **认知 OS**（llive 的 4 层记忆）：把经验畳进分层化的记忆，在后面的任务中回溯。

领域虽不同（文本预测 / 图像生成 / 智能体），却共有**"一致性，是靠把过去保持在记忆里再复用而获得"**这副骨架。这就成了"记忆机构并非 LLM 特有的小技巧，而是支撑生成·推理一致性的普遍部件"这一主张的、**来自其他领域的旁证**。

用 ablation 的数字来看其贡献（均为论文 self-report）：

| 指标 | 有记忆 | 无记忆（ablation） |
|---|---:|---:|
| CIDS（角色一致性系） | 0.619 | 0.582 |
| CSD（角色相似系） | 0.668 | 0.547 |

移除记忆，一致性指标就下降。**"记忆对一致性有效"**这件事，被另一个领域用自己的实验展示了出来——这就是旁证的内容。

## ★honest 的必读注记（为了不高估 MangaFlow）

若把这个旁证读成"所以漫画生成是 SOTA"，那就错了。为了 honest 地对待这篇论文，明确列出 4 条注记。

1. **"作画"并非 MangaFlow 本身。** 生成像素的是外部的云端扩散模型（Gemini 2.5 Flash Image / FLUX.2 9B），MangaFlow 担当的是**其控制层**（版面与角色引用的指示）。把它读成"MangaFlow 在画画"是错的。
2. **Layout IoU 100% / Coverage 99.98% 不在同一擂台。** 这是**在设计上以几何坐标明示放置、因而近乎自明的自制指标**，并非与从像素生成的基线在同一擂台比较的数字。况且是自己设计的测试，因而也需注意容易跑出有利数字这一点。
3. **商用站点 mangaflow.studio 是与本论文无关的另一产品。** 不要因为名字相同就混淆。
4. **同行评审前 v1·零引用·无 GitHub 公开记载。** 即第三方验证尚未完成（用信任的阶梯来说，处于 self-report 的台阶）。

可作为旁证的，仅到"记忆对一致性有效的方向性"为止，**而非绝对的性能主张**——这条界线就是 honest disclosure。

## 另一处接续 —— MangaFlow 的"弱点"，印证了另一项工作的存在意义

MangaFlow 也写明了自己的局限。**"在 stylized（被样式化）的脸上，说话者归属与气泡放置都很困难"**。也就是说，对于被漫画式变形夸张的脸，"谁在说话""气泡放在哪里"都很难。

这恰恰是我另一项工作（漫画分格理解基准，尤其是去戳"说话者 ≠ 画面中央的被摄主体"这类 hard case）**所瞄准的那个弱点**。也就是说，MangaFlow 自认的局限，成了"**在被样式化的画上，说话者·发话的归属是尚未解决的难点**"这一基准存在意义的外部印证。生成侧（MangaFlow）说"这里难"的地方，与理解侧的基准应当评估的地方相一致。弱点的坦白，反过来印证了另一项工作的存在意义。

## 第 3 章的带走要点 —— 看到"记忆机构"就把骨架与领域分开读

若一个新的生成 AI 标榜"保持一致性的记忆"，请把下面分开来看。

1. **骨架是什么**：是不是"把过去畳进记忆、事后回溯"这一普遍部件（多半是）。
2. **是哪个领域的一致性**：是文本的上下文，是图像的角色，还是智能体的经验。骨架相同，奏效的指标与代价也不同。
3. **数字的擂台**：那个一致性指标，是与基线在同一擂台测的，还是设计上自明的自制指标。

> **检测信号**："凭记忆保持一致性"很强，但是普遍的骨架。新颖性不在"骨架"，而在"**在哪个领域·如何畳**"。自制指标的 100%，要怀疑其擂台。

### honest 的保留（第 3 章）

记忆机构不是 LLM 的小技巧。**它是支撑生成与推理一致性的、跨领域的普遍部件**。正因如此，FullSense 才"把记忆置于 architecture 的中心"（llive 的 4 层记忆）。不过——一如本连载的做法——MangaFlow 的数字是同行评审前的 self-report，可作为旁证的**仅到方向性为止**。骨架的普遍性可以支持，但个别的性能主张，要等第三方验证，我们守住这条界线。

# 着陆 —— 把 honest disclosure 扩展到行业与生态系统的轴上

3 个章节看似各说各话，实则被一根线串在一起。**支配项，往往在技术之外。**

- **许可（第 1 章）**：性能再好，商用条件不合也无法采用。把"open"一词拆成 3 个问题。
- **成长（第 2 章）**：能学的再多，没有拦阻错误的机制就会"越用越退化"。把责任置于 architecture。
- **记忆（第 3 章）**：记忆这副骨架是普遍的，但新颖性在于"在哪个领域·如何畳"。自制指标的 100%，要怀疑其擂台。

而且对这 3 者，我都套用了同一条纪律 —— honest disclosure。本连载本就是从"用家用 CPU 的极小模型，怀疑测法、展示败绩"起步的。本文是把那条纪律，**不仅扩展到自己的实测值，还扩展到行业的数字、其他公司的主张、其他领域的旁证**。

- 引用其他公司的数字（Hermes 的 star）时，也怀疑自己的引用值，撤回了过大的值。
- 引用其他领域的数字（MangaFlow 的 ablation）时，也明确写明擂台的不同以及它处于 self-report 的台阶。
- 斩向竞争对手的刃，最后必定指向自己（llive 也未经证明）。

"是 open 所以放心""越用越聪明""凭记忆得出一致性" —— 每一句都很迷人，但不把那一句信到底，而是把前提一项项验收。不只是数字，连同许可、设计思想、跨领域的旁证，都贯彻同一条 honest disclosure。这，就是为了不漏看技术之外的支配项而该有的做法。
