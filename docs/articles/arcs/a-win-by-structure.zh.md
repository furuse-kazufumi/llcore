## 引言 —— 不是「降 bit」,而是「攻击结构」

想让 AI 变轻时,人们首先会想到「把内容压缩、削薄」这一面。把权重从 fp32 降到 int8,再到 2bit。我也是这样。我勤勤恳恳地削减着模型的权重。

然而,在没有 GPU 的家用 PC 上不断累积实测后,我陆续发现,我所削减的项 **本来就不是支配项**。真正起作用的不是「降 bit」,而是「**选择一种从一开始就不持有那种越长越膨胀的项的架构**」「**测量并攻击最大的脚手架**」这种更加结构化的选择。

这篇文章,把这个领悟分 4 段交付。

1. **a7 —— 架桥:** 把 recurrent(RWKV/Mamba)作为「用定常状态搬运过去」的状态空间模型来阅读,就会明白那是 60 年前控制工程的重演。
2. **a8 —— 动态支配项:** 拉长上下文长度,Transformer 在内存和时间上都超线性膨胀,而 recurrent 保持平坦(实机实测)。
3. **a9 —— 静态支配项:** 在用 int8 削掉几 MB 的旁边,torch 运行时却吃掉了 184MB。在改写成 Rust 之前,先测量支配项。
4. **a11 —— 普适教训:** 测试 flaky 是设计的气味。把判定分离成纯函数。

贯穿始终的是「**别攻击 bit,要攻击架构/支配项**」。那么,我们依次过桥。

## 第 1 部(a7)—— 控制理论早就解决了「用定常状态搬运过去」

## 引子 —— 我的计测值,早已写在 60 年前的教科书里

某个夜晚,我在没有 GPU 的家用 PC 上做着这样的实验。

「把上下文长度 T(模型一次能看到的 token 数)从 256 拉长到 2048,即 8 倍,推理中的内存实际使用量(peak working set)会怎么变化?」

我隔离到另一个进程,测量了 OS 报告的实际 RSS(Resident Set Size)。结果如下。

| 上下文长度 T | GPT(Transformer)peak WS | Recurrent peak WS | RWKV peak WS |
|---|---|---|---|
| 256 | 229.8 MB | 205.0 MB | 215.3 MB |
| 512 | 247.3 MB | 205.1 MB | 216.0 MB |
| 1024 | 330.5 MB | 204.8 MB | 215.7 MB |
| 2048 | **607.9 MB** | 204.8 MB | 215.2 MB |

(`scripts/recurrent_runtime_rss.py` / `out/recurrent_runtime_rss.json`。Windows 11 / Python 3.11 / torch 2.12.0+cpu。)

把上下文变成 8 倍,**Transformer 的 peak 膨胀到 ×2.65,而 Recurrent 与 RWKV 是 ×1.00,即平坦**。减去固定的 baseline(~205MB = torch 运行时 + 权重),只有 Transformer 的「依赖于上下文而增长的成本」从 ~25MB → ~403MB **超线性**地拉伸(仅 1024→2048 就 +277MB)。

> **掰开揉碎(working set 是什么):** 进程「此刻实际加载到物理 RAM 上的页面」的量。
> 只在磁盘上、或仅仅是已申请的内存不计入。请把它理解为「实际正在触碰的内存的实量」。
> peak WS 是其最大值。处理长文本时内存是否会不够用,起作用的不是申请量,而是 **这个实际使用峰值**。
> 所以不是「分析上应该是这样」,而是特意用 OS 报告的 RSS 来佐证。

> **计测的 honest 保留(没有做项分解):** 把这个「超线性」读作「二次项 O(T²) 在大 T 时开始占主导」,
> 是 **从 KV 缓存线性、attention 矩阵二次这一分析模型而来的解释**。我所测量的只是
> 进程的 **合计 peak RSS**,而 **并没有把这个增量项分解为「KV 线性分」「attention 二次分」「中间缓冲分」来实测**。
> 观测事实仅到「Transformer 的上下文依赖成本超线性拉伸」为止,
> 而「那个超线性是二次项的显现」是基于分析模型的解释,我把两者区分开来。

### 在时间轴上也出现相同的走向(scaling 指数)

不只是内存,**推理所需时间**也用相同的 T 扫描测量了(`scripts/recurrent_latency_sweep.py` / `out/recurrent_latency_sweep.json`,每点测量 11 次,`torch.set_num_threads(1)`)。把 T 从 128→2048(×16)拉长时的 **scaling 指数 p**(用 time ∝ Tᵖ 的 log-log 最小二乘估计。抗拥塞的 min 基准)为:**GPT 是 p≈1.37(明确超线性,偏向 O(T²),×16 上下文为 ×45.6)/ Recurrent 是 p≈1.00 / RWKV 是 p≈0.99(两者都几乎线性,O(T),×16)**。内存上看到的「Transformer 随上下文膨胀 / recurrent・RWKV 结构上轻」,**在时间轴上以相同走向**再现了。

> **honest 保留(cross-mode 的绝对 ms 不可比):** recurrent/RWKV 在这里是用 **Python 的 per-step 循环**(T 次函数调用)测量的,解释器调用开销占主导 ——「recurrent 更快/更慢」用绝对值来说毫无意义,应当读取的只是 **每个 mode 内部的增长方式(scaling 指数)**。另外,起初 repeats=7 时 RWKV 的 T=128 因 startup 噪声成为异常值,把斜率弄脏了(p≈0.5),但 **增加到 repeats=11 后 RWKV 也收敛到 p≈0.99** —— 我不删除那个噪声点,而是连同「增加测量来压平」的经过一起保留。

![推理延迟的 scaling(双对数)。各 mode 以 T=128 归一化,只比较增长的「形态」。GPT(红)在 ×16 上下文下为 ×45.6,偏离理想线性(虚线 p=1)之上而超线性。recurrent 与 RWKV(绿,几乎重合)在 ×16 上下文下为 ×16(p≈0.99〜1.00),沿虚线线性。takeaway = 不是快慢的胜负,而是「拉长时各方式会变得多陡」这一癖性因结构而不同。](../../../assets/articles/llcore_latency_scaling.svg)
> 各 mode 以自身的 T=128 归一化,所以看的只是「上升的陡峭程度」。只有 GPT 从理想线性(p=1 的虚线)偏离向上 = 超线性。recurrent 与 RWKV 几乎重合并沿虚线 = 线性。

### 更锋利的轴 —— decode(逐 token 生成)与 amortization

到此为止都是「把长度 T **一次性合并** forward」的 prefill/batch 成本。但支配聊天体感延迟的,是 **在已有 T token 上下文的状态下,产出下一个 1 token** 的 decode 成本。在同一进程、同一模型、同一条件下,**对 prefill(构建状态/读取全上下文)与 decode(下一个 1 token)两者都**计时了(`scripts/decode_latency_sweep.py` / `out/decode_latency_sweep.json`。**计测在无内存压力的干净 runner** 中进行)。

实测(n_embd=256/L4,T=128→2048・×16)如下:**Recurrent 与 RWKV 在 prefill 中以 O(T) 增长(×15.6 / ×17.5,指数 p≈1.0),但在 decode 中落到平坦 O(1)(×0.98 / ×1.10,p≈-0.002 / 0.03)**。另一方面 **GPT 在 prefill 与 decode 上,无论哪个 T 都几乎一致**(各 T 下 prefill≈decode,例如:99≈96ms / 958≈957ms),且两者都以 **相同的指数 p≈1.37 增长**。这个 **GPT 的 decode 指数(1.365)与 prefill 指数(1.372)恰好一致**,正是「无 cache 的 GPT 的 decode 与 prefill 是同一计算」的最佳佐证。

![prefill(状态构建 O(T))vs decode(下一个 1 token O(1))的 per-token 成本(双对数)。在同一 run 内计测。recurrent / RWKV 即便 prefill 右肩上扬(p≈1.0, O(T)),decode 也落到平坦(p≈0, O(1))= amortization。GPT(无 KV cache)的 prefill 与 decode 重合(p≈1.37, 不可分离)= 每个 token 重新 forward 全上下文。takeaway = 生成越长,recurrent 的「只给状态加一手」越有效。](../../../assets/articles/llcore_decode_latency.svg)

**核心是 recurrent 的 amortization。** 这里所说的「状态(state)」,请理解为 **把至今的全部汇总成的固定大小的手账**。recurrent 能 **分开支付**「构建上下文(prefill,用 T 个 token 把状态更新 T 次 = O(T))」与「给构建好的状态加 1 手(decode,O(1))」。在长生成中 prefill 只在最初一次,之后的每个 token 都是 O(1) —— 这决定了 streaming 的体感。GPT(无 cache)做不到这种分离,**decode 的 1 step 结果上与 prefill 同样成为「全上下文的重新 forward」**。**因为是在同一个 run 里测的,这个「只有 recurrent 从 O(T)→O(1) 落下,GPT 不落下」不是跨 run 比较,而是作为直接对比呈现的。**

> **honest 保留:**(1)与 prefill 一样,**cross-mode 的绝对 ms 不可比**(recurrent/RWKV 是 Python per-step 循环计测)。(2)**这个 GPT 不带 KV cache**。生产的 LLM serving 用 KV cache 把 decode 降到 O(T)/token,但 **即便加入 cache,GPT 的 decode 也会随 T 持续增长,与 recurrent 的 O(1) 平坦在性质上是两回事**。(3)GPT 的指数停留在 ~1.37 而非理论上的 2(O(T²)),是因为在这个小模型(n_embd=256)上,二次项尚未进入完全支配的 regime。

看到这个差异时,我一瞬间以为它是「新发现」。但不是。这是 **1960 年代的控制工程把「将可观测的系统,以有界的状态搬运」这一问题整理到极致**的重演。RWKV 和 Mamba 所属的 **状态空间模型(State-Space Model, SSM)** 的「S」,就是 State(状态)的 S。这不是偶然。

## 先看 Transformer 一侧 —— 为何随上下文膨胀(KV 缓存这种「全部留着」的设计)

Transformer 的核心是 **self-attention(自注意力)**。处理新 token 时,用内积测量它与此前所有 token「有多大关系」,并对关系强的进行加权累加。长处是 **无论位置都能严格匹配**。对「3000 token 之前出现的专有名词」,也能无衰减地直接访问。代价是 **不把过去全部留着就无法匹配**。它持续把每个 token 的 Key(键)与 Value(值)作为 **KV 缓存**保留。

> **掰开揉碎(KV 缓存是什么):** attention 从每个 token 生成 Query(询问)・Key(键)・Value(内容)
> 三者。逐 token 推进生成时,每次都重新生成过去全部的 Key 与 Value 是浪费,所以
> 把生成过的 Key/Value 存起来。这就是 KV 缓存。**它是方便的工作内存,但 token 越多
> 就越线性地持续增长**。请把它理解为「把过去的全部观测原样保管的非压缩内存」。

对上下文长度 T 的内存增长方式,用结构图(从 config 计算的理论值)给出如下。

| T(上下文长度) | Recurrent state(实测) | RWKV state(实测) | GPT KV 缓存(分析) | GPT attention 矩阵(分析) |
|---|---|---|---|---|
| 64 | 2,048 B | 10,240 B | 262,144 B | 65,536 B |
| 1024 | 2,048 B | 10,240 B | 4,194,304 B | 16,777,216 B |
| 倍率(上下文 ×16) | **×1.00** | **×1.00** | **×16(线性)** | **×256(二次)** |

(`scripts/memory_footprint_harness.py` / `out/mem_footprint.json`。state_bytes 是实际字节测量,KV/attn 是源自 config 的分析值。)

Transformer 有两个会增长的东西。**KV 缓存** 对 T **线性**(×16 上下文为 ×16),严格长上下文 attention 的得分矩阵是 T×T,所以对 T **二次**(×16 上下文为 ×256)。引子里实机 peak RSS 之所以「上下文成本从 ~25MB→~403MB 超线性」,可以解释为在大 T 时 **这个二次项(O(T²))开始占主导**(不过如前所述,这是从分析模型而来的解读,而非项分解的实测)。

> **honest 保留:** 实现上 GPT.generate 内部会把上下文截断到 block_size(crop),所以仅仅跑起来是有界的。
> 上面的「线性・二次」是 **拉长 block_size 以严格地对长上下文做 attention** 时所需的量。准确地说
> 不是「Transformer 必然爆炸」,而是「**只要不放弃严格长上下文**,就是按上下文长度线性/二次支付成本的结构」。

## recurrent 一侧 —— 为何平坦(把过去「折叠」进有限的状态)

recurrent 模型不把过去全部留着。取而代之,它持有 1 个 **固定大小的状态 `s`**,每当新观测到来就更新 `s`。

```
s_t = f(s_{t-1}, x_t)      # 状态,从前一状态与新输入更新
y_t = g(s_t)               # 输出,从当前状态生成
```

要点是,`s_t` 的大小 **与 T 无关而恒定**。处理 10 个 token 也好,处理 1 万个 token 也好,状态张量的字节数相同。上表中 recurrent state 始终是 2,048 B、RWKV state 是 10,240 B 而恒定,正是这个原因。

> **掰开揉碎(做菜的比喻):** Transformer 是「把至今用过的所有食材全部留在冰箱里」的做法,
> recurrent 是「往一口锅里接连放料持续炖煮,只把锅里的内容(=状态)传给下一步」的做法。
> 锅的大小是定的,所以炖多久放料的地方都不会增加。**不过炖得越久,最初放入的
> 食材的味道就越淡**(= 旧信息的损失)。这个「变淡」连接到后半部分会崩坏的地方。

## 在此过桥:状态空间模型(SSM)与控制理论

从这里开始是第 1 部的核心。recurrent 的「把过去折叠进定常状态」,可以用 **控制工程的状态空间模型(SSM)的词汇**重写。这在 literature 上是正统的衔接。"Structured State Spaces" 是 SSM 系 LLM 的前身 **S4 论文**(Gu et al., 2022)的标题,而 **Mamba**(Gu & Dao, 2023)是其直系发展。两者中 **状态空间模型(SSM)都是 signal processing / control 的标准概念**。

另外,本节的「可以重写」是 **结构性类比**,而非数学等同性的主张。桥成立于「以逐次状态更新把过去折叠为有限表示」这一骨架层面,并不意味着 RWKV/Mamba 字面上就是线性时不变的状态空间模型或 Kalman 滤波器。

### 状态空间模型是什么(控制工程 60 年的标准形)

线性时不变的状态空间模型,教科书上这样写。

```
x_{t+1} = A x_t + B u_t      # 状态方程:下一状态 = A×当前状态 + B×输入
y_t     = C x_t + D u_t      # 观测方程:输出 = C×状态 (+ D×输入)
```

- `x` = **状态(state)**。系统的「把至今全部历史汇总而成的有限维向量」。
- `A` = 状态转移矩阵。决定「把过去的状态多大程度地继承到下一步」。

决定性的是,**`x` 是有限维且固定大小**。控制工程从一开始就以「把无限持续的输入历史,压缩进有限的状态来搬运」为前提构建。RWKV/Mamba 的 `s_t = f(s_{t-1}, x_t)`,正是这个状态方程的(带非线性门的)亲戚。

> **掰开揉碎(为何控制工程是这个形态):** 在工厂的设备或火箭的姿态控制中,没有余裕把过去的传感器值
> 全部保存并每次参照。需要做成「只要知道当前状态,就能决定下一步怎么动」的形式。
> 所以控制工程从一开始就把「**把过去全部折叠进有限的状态**」作为出发点。
> LLM 的长上下文问题中,recurrent 重新发现的,正是这个 60 年来的出发点。

### 可观测性 —— 「把过去折叠进有限的状态,真的够吗?」

控制工程里有 **可观测性(observability)** 这一概念。粗略地说就是「看输出 `y` 的历史,能否唯一地复原内部状态 `x`?」这一性质。这正好对应 recurrent 的「定常状态真的没问题吗」这一不安。**若状态维度对于想区分的过去的辨别而言不足**,则本应区分的两个过去会被压扁成同一个状态(变得不可观测)。反之,若状态维度对于必要的辨别而言充足,则即便是定常状态,必要的区分也能保持。Transformer 之所以「把过去全部留着」,也可以读作 **用蛮力始终保证** 可观测性。

### Kalman 滤波器 —— 「把观测持续折叠进状态更新」这一思路的鼻祖

1960 年,鲁道夫・卡尔曼博士(Rudolf E. Kálmán)定式化的 **Kalman 滤波器**(*A New Approach to Linear Filtering and Prediction Problems*, 1960),正是「把接连到来的观测,持续卷入固定大小的状态估计(与协方差)」的算法。每当新观测到来,不重算过去全部,只更新当前的状态估计。RWKV/Mamba 之所以「丢掉 KV 缓存,持续更新固定状态」,在结构上与 Kalman 以来的「逐次状态更新」思路是同一骨架。Transformer 的 KV 缓存则是其对极 —— **不折叠观测、原样全部囤积的非压缩表示**。

> **★这里是「桥折断的地方」之一(字面上并非 Kalman):** 把 RWKV/Mamba 断言为「就是 Kalman 滤波器」
> 是 **错误**的。Kalman 滤波器是线性高斯系的最优估计,拥有明确的观测模型、噪声协方差、
> 最优性的证明。RWKV/Mamba 拥有 **非线性门**(tanh / sigmoid / 输入依赖的转移),矩阵是
> 从数据学习的,也没有最优性的保证。两者共享的只是「**以逐次状态更新把过去折叠为有限表示**」
> 这一结构性骨架。本文的主张始终是 **结构性类比**,而非数学等同性。

### 所以 recurrent 的「平坦」不是 config 的偶然,而是结构性必然

到这里就明白了,引子里「recurrent peak WS 与 T 无关而 ×1.00」,并非我实验设定的偶然。状态空间模型 **从定义上** 状态就是有限维固定。上下文无论怎么拉长,搬运的只是同一大小的 `x`(状态)。**两者的差异不是实现的调整幅度,而是如何表示过去(折叠还是囤积)这一架构的根本选择**。

## ★最重要的 fix —— 不要把 ρ(收缩性)「过度连接」

这类跨域文章最容易犯的混淆,我提前打掉。一搬出控制工程,就会不由自主地 **把「稳定性(收缩性)」与「学习紧贴稳定边界」混为一谈,编成一个漂亮的故事**。这是错的。

**(A) 收缩映射 ρ<1 = 稳定性的证明(结构上要求的东西)**
在 llcore 的另一个 Arc(带验证的可塑性)中,我们给 frozen 的 LLM 的隐藏状态后接一个小的 recurrent 适配器 `s' = decay⊙s + (1−decay)⊙tanh(Ws + x)`,并带证明地保障其稳定性。若雅可比 `J` 的谱半径 `ρ(J)<1`,则状态更新成为 **收缩映射**,小的扰动随时间衰减(echo-state property)。llcore 的证明器(`cert_inf`:‖J‖_∞<1、`cert_two`:在全顶点 σ_max<1、`cert_sdp`:共通 Lyapunov LMI)**只让满足 `ρ(J)<1` 的东西以 fail-closed 通过**。`empirical_rho`(从下方逼近特征值的独立 oracle)检查证明的健全性。

> **掰开揉碎(收缩映射是什么):** 当把输入稍微偏移时,输出的偏差 **必定小于原来的偏差** 的映射。
> 无论重复多少次偏差都不扩大,所以系统不会失控而是落定到一点。`ρ<1` 就是它的数学合格线。

**(B) 学习紧贴稳定边界 ρ≈1(与表现力的张力,被观测到的现象)**
在另一个实验(M2)中,出现了 **fitness 最优个体的 `empirical_rho` 紧贴 1.000** 的观测。这是「想最大化表现力时,状态更新会靠向 **稳定性的悬崖边(ρ→1)**」,即在水库计算与 recurrent 学习中已知的 **表现力 vs 稳定性的权衡** 的显现。

在此「控制理论说 `ρ<1` 是稳定的条件,学习也走向 `ρ≈1`。所以控制理论连 edge of chaos 都预言了!」会 **让人想缝合成一个美丽的故事**。这就是过度连接。两者 **方向相反**。(A) 是「**留在** `ρ<1`」(我们施加的上限规范)。(B) 是「`ρ` **靠向** 1」(优化所展现的行为)。因为用了同一个记号 `ρ`,乍看像是连着的,但 **在逻辑上是独立的**。

> **所以本文正确的说法:** 控制理论在 60 年前就解决了 **(A)「用定常状态搬运过去 + 以 `ρ<1`
> 刻画其稳定性」**。另一方面 **(B)「表现力紧贴稳定边界 `ρ≈1`」,是稳定性与表现力的
> 张力,即控制与机器学习双方各自都知道的已知权衡**,而非从 (A) 自动得出的
> 东西。区分两者之后再并列 —— 这才是 honest 的衔接。

## ★桥折断的另一个地方 —— recurrent 在 capability 上「可能」劣于 Transformer

至此写了 recurrent 的 **内存轴上的结构性胜利**。但若以「所以 recurrent 胜过 Transformer」收尾,那就是引水入自家田,有悖于连载顶部的 caveat。如实写下。

在 llcore 的进化探索 Arc 中,测量了 recurrent 系适配器的 **capability(智能 —— perplexity / cross-entropy 上能否超过梯度)** 的结果,地形是 **NULL_TIE / NEGATIVE**(进化相对 baseline 无显著差异〜反而微害)。也就是说 llcore 自身承认「**在这个特定的实验设定下,无法确认 recurrent 进化的 capability 胜算**」(`project_llcore_memory_efficiency_pivot`,把北极星从 capability 转向 memory 的直接理由)。

> **honest disclosure / 来源的边界:** 接下来叙述的 literature 一般倾向,与刚才叙述的 llcore null 结果,
> **出处不同**。前者是 **SSM 文献中一般指出的倾向** = 本文未用 llcore 实测直接验证的
> 外部知识。后者(NULL_TIE / NEGATIVE)是 **llcore 在特定实验设定下的自前 null 结果** = 来源是 llcore 实测。

那个 literature 一般倾向是这样 —— KV 缓存「严格保持全部观测」的性质,在 **无关位置的严格 long-range recall(长距离的准确召回)** 上,容易胜过 recurrent 的 lossy 压缩状态,这在 SSM 文献中被一般地指出。在重视 recall 的任务上,纯 recurrent 常被认为劣于 Transformer,正因如此,许多实用 SSM 才走向交织 attention 层的 **hybrid**,这是文献上常见的整理(例如:Jamba 是把 Mamba 与 Transformer 交替堆叠的混合)。

做菜的比喻里提到的「炖得越久最初的食材味道越淡」—— 那就是在 capability 一侧起作用的症状。**当状态维度对于必要的辨别而言不足时**,在把过去折叠进固定大小状态的过程中,某处本应辨别的过去被压扁。在内存上取胜的机制,当状态维度不足时,也可能成为 capability 弱点的源头。

**所以本文的主张「限定在内存轴」。**「recurrent 与上下文长度无关而以定常内存运行」在结构上正确(我的实测 ×1.00 所示)。但「recurrent 综合上优于 Transformer」我们 **不说**。恰恰相反,llcore 在承认这个设定下无法确认 capability 胜算之后,把北极星移向了能取胜的轴(内存效率)—— 这篇文章就立在那个诚实的败北之上。

## 第 1 部的比喻 —— 「全文保存日记的人」与「只更新摘要的人」

两个人每天都在写日记。

- **A 先生(Transformer)** 把每天的事 **原封不动全文** 攒在笔记本里。无论几年前的事,翻页就能一字不差地准确回忆。代价是笔记本一年年变厚,某天终于塞不进书架了(KV 缓存的线性膨胀)。而且因为有「把过去的全部页面相互比对」的习惯,所以手续随页数的平方增长(attention 的 O(T²))。
- **B 先生(recurrent / SSM)** 每晚只把 **当天的事折叠成一句摘要,更新仅一张「当前汇总卡」**。卡片过了多少年都还是一张。书架完全不增加(定常状态 ×1.00)。这是控制工程师和卡尔曼博士在 60 年前整理出的「这样往往就够了」的做法。

**这个比喻在哪里折断:**(1)B 先生的卡片是 **摘要**,所以被一字不差地追问「3 年前几月几日谁说了什么」时,会输给 A 先生(lossy 压缩 = capability 的弱点)。(2)若摘要栏(=状态维度)对于必要的辨别而言太窄,本应区分的两天会被压扁成同一摘要(可观测性的丧失)。塞入过多信息时,卡片更新会靠近稳定的悬崖边(ρ≈1)—— 不过这与「把卡片保持为一张」的设计是两回事,不可混淆。(3)归根结底,B 先生并不是在「做与卡尔曼博士相同的事」,只是骨架相似,而非线性、无最优性保证。

比喻是理解的脚手架,而非证明。在指明脚手架崩塌之处后再使用 —— 这是本连载的做法。

## 第 2 部(a8)—— 把上下文变成 4 倍,Transformer 的内存膨胀到 5 倍,recurrent 纹丝未动

第 1 部架起了「控制理论早就解决了『用定常状态搬运过去』」这座桥。第 2 部是它在 **实机内存上的结果**。**动态支配项** —— 把随上下文长度增长的项,用曲线展示。

在另一篇文章里,我写过想测量长上下文的检索性能,结果 **家用机器(RAM 3.6GB)的内存先撑不住了** 的事。2048 token 的 full-attention forward 把 working set 膨胀到 3.9GB 而发生 swap。那看似事故,其实是 **结构早已预告的必然**。

> **先说结论:** 把上下文长度从 1024 → 4096 token(4 倍)时,Transformer(GPT)的 peak 内存
> 从 331.8MB → 1673.0MB,膨胀约 **5.04 倍**。相同条件下 recurrent 是 205.4MB → 205.6MB,即 **纹丝未动**。

## 数字全公开 —— 不看点,看曲线

准备了 3 个架构的轻量模型(GPT / recurrent / RWKV),一边改变上下文长度,一边 **隔离到另一进程实测 peak working set(WinAPI 的 `PeakWorkingSetSize`)**。`scripts/recurrent_runtime_rss.py --lengths 128,256,512,1024,2048,4096`(实机 2026-06,极小模型 n_embd 256 / 4 层 / 8 head)。不看单点,而是用 **32 倍范围的曲线** 来看。

| 上下文长度 L | GPT peak WS | recurrent peak WS | RWKV peak WS |
|---:|---:|---:|---:|
| 128 | 222.3 MB | 205.5 MB | 215.4 MB |
| 256 | 230.7 MB | 205.2 MB | 215.7 MB |
| 512 | 247.7 MB | 205.3 MB | 216.1 MB |
| 1024 | 331.8 MB | 205.4 MB | 216.0 MB |
| 2048 | 607.9 MB | 205.6 MB | 216.0 MB |
| 4096 | **1673.0 MB** | **205.6 MB** | 215.9 MB |
| **128→4096(×32)的倍率** | **×7.53** | **×1.00** | **×1.00** |

**曲线的形态是最好的证据。** GPT 的膨胀率依赖于计测范围:128→512(×4)是 **×1.11**,几乎平坦 —— 这个区域由固定权重(模型本体)支配 peak,attention 的 O(L²) 项还埋在误差里。然而 512→4096(×8)是 **×6.75** —— 这里二次项超越了固定底,曲线骤升。「上下文 ×N 内存 ×M」这种单一标题,**M 会因从哪里开始测而剧变**(同一装置既可以是 ×1.11 也可以是 ×6.75)。所以不出单点而出曲线。recurrent / RWKV 在全域贴在 205 / 216 MB(×1.00),用 32 倍范围佐证了定常状态与上下文长度无关。

> 补充:1024 与 2048 的点与另一日的独立 run(`out/recurrent_runtime_rss_long.json`)以 0.1 MB 之差一致,跨 run 可复现性也已确认。

![上下文长度 128→4096(对数轴)下,GPT 的 peak WS 在短上下文(128→512)是 222→248MB 几乎平坦(固定权重底支配,×1.11),却在长上下文骤升到 608→1673MB(二次项显现,×6.75),而 recurrent/RWKV 在 205MB 全域平坦(×1.00)的折线图。takeaway = 膨胀方式不是恒定的,从哪里开始测倍率会剧变 = 不看点,看曲线。](../../../assets/articles/llcore_context_memory.svg)

*图:横轴为对数。GPT(红)在短上下文被固定权重底掩盖而几乎平坦,在长上下文二次项露脸而骤升(全范围 128→4096 为 ×7.53)。recurrent/RWKV(绿)以定常状态全域平坦(×1.00)。T=4096 时 GPT 是 recurrent 的 8.1×。*

看点有 3 个。

1. **GPT 超线性膨胀。** 上下文 4 倍(1024→4096)是 **内存 5.04 倍**,全范围 32 倍是 **7.53 倍**。因为 attention 的得分矩阵是 L×L,即按 **O(L²)** 增长。增长方式不是恒定的,上下文越短越被固定权重掩盖而平坦,越长二次项越露脸而尖锐。
2. **recurrent 与 RWKV 不动。** 上下文 4 倍也是 **×1.00**。因为把过去折叠进固定大小的状态,原理上没有依赖上下文长度的项。
3. **T=4096 时 GPT 1673MB 是 recurrent 205MB 的 8.1 倍。** 外推则 **T=8192 时 GPT 约 6.5GB** —— 在我的家用机器(3.6GB RAM)上 **是物理上装不下的墙**。而 recurrent 仍是 205MB,纹丝不动。

我的机器 swap 的 3.9GB,正是这条曲线上的一个点。不是事故,而是 **如 O(L²) 所预告**。

> **掰开揉碎(开会的比喻):** 10 人的会议上,若每个人都一一确认「其他所有人的发言」后再说话,确认的
> 组合就按人数的 **平方** 增长(5 人是 25 种,10 人是 100 种)。这就是 Transformer 的 O(L²)。
> 而 recurrent 是「传一本笔记,各人只补写要点再传给下一个」的做法 —— 笔记的厚度即便人数
> 增加也不变。不过这本「汇总笔记」是 lossy 的,无法一字一句复原(平坦内存的代价)。

## 为何会这样(结构的话)

GPT 的 attention 是「全 token 看全 token」的全配对。token 有 L 个,看的组合就是 L×L,所以内存和计算都是 **O(L²)**。而且 KV 缓存还以 **O(L)** 持续吃内存。recurrent / RWKV 思路相反,一边逐个读过去 **一边卷入固定大小的状态向量**,把它搬到下一步。状态的大小不依赖上下文长度(内容是数 KB 的常量)。这正是第 1 部的「控制理论的状态空间模型」。理论说的「能用定常状态搬运过去」,在实机的 peak WS 上作为 **平坦的直线** 呈现了出来。

## 不掩盖的免责声明(这个数字的局限)

- **是极小・未训练模型。** n_embd 256 / 4 层的随机初始化模型。内存行为由架构决定而不依赖训练状态(所以对计测是妥当的),但请不要把 **绝对值** 直接套到大厂 LLM 上。应当读取的是 **增长的趋势**。
- **peak WS 是「素 torch 运行时 + 固定权重 + 上下文依赖缓冲」的合计。** recurrent 的「平坦 205MB」大半是 torch 的 baseline(第 3 部要测的支配项),定常状态本身是 KB 量级。也就是说 205MB 不是「定常状态重」,而是表明「**没有会增长的项**」。
- **GPT 在实际运用中用 block_size 截断上下文**,所以不会如此直接地膨胀。本测量看的是「若要严格保持长上下文,最少需要多少」的必需量。

## 第 2 部的教训 —— 比起「快」,更要「可预测性」

在长上下文的时代起作用的,不是峰值性能,而是 **「能预测内存对上下文长度如何表现」**。GPT 又快又强。但上下文一拉长,内存就以 O(L²) 走向 **不可预测的悬崖**。recurrent 即便慢,**来多少 token 都是 205MB 平坦不变** —— 可预测。

> 量化是「把现有的东西削薄」。
> 架构选择是「从一开始就不持有会增长的项」。
> 上下文越长,后者越在结构上甩开前者。

这个「量化(削 bit)有天花板,本命是选择不持有动态支配项的架构」的结论,直接接到下一个第 3 部 —— **静态支配项**。

第 2 部是「把上下文拉长,Transformer 的内存以平方膨胀」这一 **动态支配项** 的话。第 3 部是它的背面,**静态支配项** 的话。

契机是一句常见的话。

> 「要彻底追求内存效率,干脆用 Rust 改写吧?那样效率更高吧。」

听起来有道理。但我已经决定,对这种「换成○○效率就会提高」**不自动相信为正确**。所以测了。结果颠覆了我优化的前提。

> **在用 int8 量化把模型权重削到约四分之一(数 MB)的旁边,Python+torch 的语言运行时,
> 即便什么都不做也吃掉了 184MB。** 我所削减的项,本来就不是支配项。

| 模型加载后 | 213.6 MB |

由此得出的比率很关键。

我曾集中于用 int8 量化「把权重变四分之一!」削掉数 MB。但整体图景是,**在 1.51MB 的本体周围,搭起了 212MB 的"脚手架"**。数 MB 的节省,在 142 倍的脚手架面前几近误差。

> 发生了这件事。

## 「攻击支配项」—— 削哪个项是全部

优化有铁则。**攻击最大的项(支配项)**。再怎么打磨小项,整体也几乎不动。

- **动态支配项** 是随上下文长度增长的 attention/KV(第 2 部测的 O(L²))。
- **静态支配项** 是这个第 3 部的 **语言运行时的 baseline(仅 torch 就 +184MB)**。

在豆模型规模上,后者(184MB 的 torch 税)占压倒性主导。如此,**真正起作用的不是 int8 的数 MB,而是如何减少这 184MB 的脚手架**。

而 **这里正是「改成 Rust?」真正起作用的地方**。lean 的 native 二进制(C++ 的 llama.cpp、Rust 的 candle / mistral.rs 等),运行时 baseline 小出一个数量级(典型为数 MB〜十几 MB)。**184MB 规模的削减**,与 int8 的数 MB 不可同日而语,直接关联到「把 working set 做得小且可预测」这一北极星。而且若是 Rust 还能自己掌控 allocator,所以「释放的 fp32 被 torch 的 caching allocator 不归还给 OS,平时的峰值降不下来」这种另一个积年问题,也能用 `madvise(MADV_DONTNEED)` 或显式释放正面击破。

## 不掩盖的反面(「Rust=效率↑」也不是自动的)

到此打住就成了「Rust 万能论」。作为 honest disclosure,明示反面。

- **Rust 既不把 int8 变小,也不把 mmap 变好,也不把定常状态变定常。** 这些胜利源自表示・OS・算法,**与语言无关**。移到 Rust 也不会改善 1 个字节。Rust 起作用的只是 **baseline(脚手架)** 这个项。
- **素 Rust 的矩阵乘,比 torch 的 BLAS(MKL/OpenBLAS)慢。** 「Rust=快」也不是自动的。要出速度,需要 candle 或 BLAS 绑定。
- **规模依赖是关键。** 184MB 的税之所以占主导,**是因为豆模型规模**。一旦变成 GB 级的权重,baseline 就相对可忽略。也就是说 **Rust 的 baseline 优势,在 llcore 实际居住的领域(小模型・小 RAM)最大,在权重支配的大规模最小**。
- **这是 llama.cpp 已经实证过的动作。** 立场上是「**再导出**」,诚实的独特性不在那里(语言),而在另一篇文章写的 cap-gate(能力门)的运用上。
- **未确证(honest gap)。** Rust/candle 版的 baseline RSS **尚未测量**。「native 则 baseline 小出一个数量级」是从文献・既有实现而来的妥当推定,最终确证需要 candle 实测。

## 第 3 部的教训 —— 在改写成 Rust 之前,测量 baseline

> 听到「换成○○效率就会提高」时,在改写之前 **测量当前的支配项**。
> 我的支配项不是 int8 能削的权重,而是 import torch 那一瞬间的 184MB。

如果不测就奔着「为了内存效率全面移植到 Rust」去跑,劳力的大半会消耗在「把与语言无关的胜利(int8/mmap/定常状态)**用 Rust 重写一遍**」上,而真正起作用的 184MB baseline 削减这一主目的会被埋没。**把目标聚焦于『把推理路径 native 化以消除 interpreter 税』** —— 那才是测了之后才看见的正确移植方针(不是奔速度,而是奔脚手架)。

优化,在打磨之前先测「哪个项大」。看似理所当然,可一边削 4MB 一边漏看 184MB 的我自己,正是最忘了这一点的人。这个「**先测再动手**」的纪律,连接到最后第 4 部的普适教训。

## 第 4 部(a11)—— 测试 flaky,不是测试的错,而是设计的信号

至此都是 AI 架构的支配项的话。最后稍换口味,是 **「测试的难写,教会了我设计的气味」** 这一普适的工程一幕。不是 AI 特有的,而是对造物全般都有效的小话题 —— 但与「测量支配项」一样,是 **别搞错症状的出处** 这一相同纪律的话。

## 想做的事,与摇摆的测试

想用 TDD(测试驱动)写一个「**只在能力检收(cap-gate)PASS 时,才保存量化后的模型**」的升级门。规格很简单:gate PASS → 写,FAIL → 不写。

然而,测试变得 **flaky(每次执行结果都摇摆)**。有时合格,有时不合格。这样就无法断言「确实能跑」。

原因是,测试对象使用的 **未训练(随机初始化)模型**。随机模型的「下一 token 预测」几乎是均匀分布。在那上面叠加 int8 量化的微小噪声,**top-1(最有力候选)就会跨越边界互换**。结果,retention(能力维持率)在合格线上下摇摆,把「PASS 时写」整个经由 CLI 测试时,PASS/FAIL 每次执行都会变。

> **掰开揉碎(top-1 是什么):** 模型作为「接下来的最有力候选」放在第 1 位的选项。候选几乎
> 并列(均匀分布)时,极微小的噪声就会让第 1 位和第 2 位互换。这就是判定抖动的源头。

在此「给测试加 retry 来蒙混」是坏招。flaky 大多 **不是测试的问题,而是设计的问题**。

## TDD 的格言 —— 「难以测试 = 设计不明确」

测试驱动开发里,有这样的经验法则。

> **测试难写时,不是测试不好,而是设计不明确,或耦合太强。**

用这个镜头看自己的代码,原因就现形了。**「是否升级的判定逻辑」与「写文件这一输入输出(I/O)」混在了一个函数里**。判定与 I/O 黏在一起,所以无法单独确认判定,每次只能走带 I/O 的非确定性路径。

> **掰开揉碎(做菜的比喻):** 想象一个明明想尝味,却把「调味」和「摆盘」用同一手做掉的
> 厨师。明明只想确认味道,每次却得做到盛进盘子才知道味道。
> 而且摆盘的成色每天有抖动,所以连味道的判定都跟着抖。我的程序正是这个。

## 修法 —— 把判定切出成纯函数

于是,把判定单独切出成 **纯函数**(相同输入必返回相同输出、无副作用的函数)。

```
_should_promote(report, force) -> (bool, reason)
```

传入 `report`(能力检收的结果)与 `force`(强制标志),只返回「是否应升级」与「其理由」。不写文件。于是 ——

- **判定逻辑**,传入手工构造的检收结果(gate = PASS / FAIL / 未测量 共 3 种 × 有无 force),可 **确定性地** 测试。
- **CLI 集成测试**,避开非确定性,**只限定于确定性路径**(「把 retention 下限设为 0.0 必定 PASS」「不指定语料必定拒绝」)。

flaky 消失了。不是给测试加了 retry,而是 **把判定与 I/O 分离了**。

![BEFORE/AFTER 对比图。左(BEFORE)是「判定」与「文件写入」黏在一个函数里,int8 噪声使 top-1 跨越边界,导致 CLI 整体测试在 PASS/FAIL 间摇摆。右(AFTER)是只把判定切出成纯函数 _should_promote → (bool, reason),分离为判定的单元测试(gate=PASS/FAIL/未测量 × force)与 CLI 的确定性路径(--min-retention 0.0 → PASS / 无语料 → 拒绝),flaky 消失。takeaway = 测试的摇摆是「把设计分开」的免费评审员。](../../../assets/articles/llcore_a11_test_smell.svg)

_把判定与 I/O 的黏连(左),通过判定的纯函数化分离(右)的前后对比。_

## 第 4 部的教训 —— 别把 flaky 当成「测试的运气不好」打发

看到 flaky 的测试,就想用「环境的错」「碰巧」打发。但很多情况下,那是 **设计混入了什么的信号**。

> 测试难写・摇摆 ——
> 那不是「修测试」,而是「**把设计分开**」的信号。

这次是「判定」与「输入输出」黏在了一起。分离后,测试变得确定,代码也变得易读。**测试的难度,是指明设计改善点的免费评审员**。在 AI 的小工具制作中,这个经典原则也照样有效。

## 整合的自我审计 / honest disclosure

作为 career-grade 的纪律,我对本 Arc 整体的主张自己开刀。

- **规模:** 所有实测值(×1.00 / ×2.65 / ×7.53 / 142× / 状态 2,048〜10,240 B / torch 税 184MB)都是 **在 CPU 上测的 0.81M〜130M 的 tiny char-LM**。无法保证 12B〜64B 的实际 LLM 会以 **相同比率** 出现相同的平坦・相同的膨胀。斜率的 **走向** 与 literature 一致,但 **绝对值的外推未获保证**。
- **计测的干净度(没有做项分解):** peak WS 是 torch 运行时 + 固定权重 + 上下文依赖缓冲的 **合计**,干净的信号是减去固定 baseline(~205MB)后的 **增量趋势**。并没有把那个增量项分解为「KV 线性分」「attention 二次分」来实测,「超线性 = 二次项的显现」是从分析模型而来的解释。
- **类比的保留:** 与 SSM / 可观测性 / 收缩映射 / Kalman 滤波器的对应是 **结构性类比**。不主张 RWKV/Mamba 字面上就是状态空间模型或 Kalman 滤波器(非线性门・学习矩阵・无最优性)。
- **ρ 的不混同:** 区分了「`ρ<1` = 稳定性的证明(施加的约束)」与「向 `ρ≈1` 紧贴 = 表现力 vs 稳定性的权衡(被观测的现象)」。从前者不会自动得出后者。
- **来源的边界:** capability 结论的 **NULL_TIE / NEGATIVE 是 llcore 的自前 null 实测**,**「纯 recurrent 在 recall 上易劣 / 实用 SSM 走向 hybrid」是 SSM 文献的一般倾向(本文未验证的外部知识)**。
- **capability 的诚实败北:** recurrent 的 capability 地形已被 llcore 自身认定为 NULL_TIE / NEGATIVE。本 Arc 的优势主张 **限定在内存轴**,而非综合的 capability 优势。
- **Rust 的未确证:** Rust/candle 的 baseline RSS 未计测。「native 则 baseline 小出一个数量级」是从文献・既有实现而来的推定,最终确证需要 candle 实测。
- **类比是一根柱子:** 只聚焦于 SSM / 控制理论这一根,没有追加 edge of chaos 或水库计算的别的类比(回避过度连接)。

## 结语 —— 不以「重演」为耻,不夸张「同一」,测量支配项

这个 Arc 里我在家用 CPU 上测的东西 ——「上下文长度 ×8 时 Transformer ×2.65 / recurrent ×1.00」「×32 时 ×7.53 vs ×1.00」「int8 本体 1.51MB 旁边 torch 税 184MB」—— 没有一个是新发现。这是 **60 年前的控制工程把「用定常状态搬运过去 + 以 `ρ<1` 刻画其稳定性」整理到极致的问题,在 char-LM 尺度上的重演**,以及优化铁则「攻击支配项」的直接应用。

但是,重演有价值。

1. **结构会通透。** recurrent 的平坦不是 config 的偶然,而是来自状态空间模型定义的结构性必然。所以能说「**这一族在内存轴上结构性取胜**」。
2. **能防止过大主张。** 借用控制理论的词汇的同时,也看见那词汇 **在哪里折断**(字面上并非 Kalman / capability 上可能劣 / `ρ<1` 与 `ρ≈1` 是两回事 / (A) 解了但 (B) 没预言)。无需用借来的权威给论调灌水。

而贯穿 4 篇的通底主题是一贯的 ——**不是「降 bit」,而是「攻击架构与支配项」**。

- 比起用量化削 int8 的数 MB,**选择不持有随上下文增长的动态支配项(O(L²))的架构**,在长上下文上效果大出一个数量级(第 2 部)。
- 在改写成 Rust 之前,**测量静态支配项(184MB 的语言运行时脚手架)**,才不会搞错该削的项(第 3 部)。
- 还有,测试一摇摆就 **测量症状的出处(设计的黏连)并分离** —— 这也是「先测最有效之处再动手」的相同纪律(第 4 部)。

LLM 的长上下文・低内存竞争,追究到底会收敛到 **「过去放在哪里、如何持有」「哪个项占主导」** 这样,控制工程与优化的古典在半世纪前面对过的问题。Transformer 用「全部留着」买位置严格性,以内存支付。recurrent/SSM 用「折叠进有限状态」节省内存,以辨别的锋利度支付。**不是哪个正确,而是在哪个轴上支付的选择**,而那张地图的 (A) 部分,控制工程早就描绘过了 —— 这就是本 Arc「以结构取胜」的过桥终点。

下一个 Arc 里,我会把这个「以结构取胜」的思想,扩展到计测纪律本身(怀疑自己胜利的 honest disclosure),以及 local / on-prem 这一 FullSense 的语境衔接。
