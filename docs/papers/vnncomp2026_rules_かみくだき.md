# VNN-COMP 2026 ルール ―― かみくだき版（まず全体像）

> これは「中学生でもわかる」入口です。正確な数値や条件は忠実訳 `vnncomp2026_rules_ja.md`、最終的には英語原文で確認してください。

---

## そもそも何の大会？

**「AI が安全だと数学で証明する道具（検証ツール）の腕くらべ大会」** です。年に 1 回。2026 年は 7 回目で、7 月にポルトガルのリスボンで開催（SAIV という学会と併設）。

### たとえ：採点競技

- 主催者が「**お題（benchmark）**」を出します。お題は「この AI、入力がこの範囲なら絶対に変な答えを出さないと証明せよ」というような問題集です。
- 各チームの **検証ツール** がお題を解き、**何問正しく証明できたか**を競います。
- 「正しく証明できた」「正しく"危ない"と見抜けた」で**加点**、**間違えると大きく減点**。時間切れは 0 点。

---

## 登場人物（3 つの役割）

1. **ツール参加者（tool author）**：検証ツールを出して競う人。← 私たちはこれでは**ない**。
2. **benchmark 提案者（benchmark proposer）**：お題を作って提供する人。**誰でもなれる。会社や個人でも、ツールを出さない人でも OK。** ← **私たちはここ**。
3. **主催者（organizer）**：大会を運営し、もめ事を裁く人。

---

## 言葉（最低限）

- **instance（インスタンス）**：問題 1 問。「AI 1 個 + 入力 + 守ってほしい条件 + 制限時間」のセット。
- **benchmark（ベンチマーク）**：問題集。instance の集まり（例：同じ AI に 100 枚の画像で 100 問）。
- **`.onnx`**：AI 本体を保存したファイル（＝設計図）。
- **`.vnnlib`**：「何を証明したいか（守ってほしい条件）」を書いたファイル（＝採点項目）。
- **unsat（アンサット）＝「安全を証明できた」**（"危ない出力"はあり得ないと示せた）。
- **sat（サット）＝「危ない例が見つかった」**（"危ない出力"があり得る）。このときは**その具体例（witness＝証拠）も出す**。
- **timeout / error / unknown**：時間切れ／エラー／その他。

---

## 採点（ざっくり）

- 正しい **unsat**：**+10 点**
- 正しい **sat**：**+10 点**
- **間違い（や証拠なし等のペナルティ）：−150 点**（← 間違えると痛い。だから「自信がないのに答える」と損）
- 時間切れ・エラー・不明：**0 点**
- 時間ボーナスは**無し**。

> ポイント：**間違いの罰がとても重い**（+10 に対して −150）。これは「いいかげんな証明を出すな、本当に証明できたものだけ unsat と言え」という設計。名誉規定（honor code）でもそう釘を刺している。

各お題のスコアは「自分の点 ÷ そのお題で一番点を取ったツールの点 × 100（％）」。総合点はお題ごとの％の合計（＝**どのお題も同じ重み**）。

---

## どうやって進む？（流れ）

1. ツール作者が自分のツールを動かす 3 つのスクリプトを用意。
2. **みんなでルールを議論し、お題（benchmark）を募集・確定**。← **私たちが提案を出す場面**。
3. 仮計測（自分で試す）。
4. 本計測（主催者が新しいランダム種で全ツールを走らせる）。
5. 結果発表 → arXiv レポートにまとめる。

---

## お題（benchmark）の出し方 ―― 私たちが関わる所

新しいお題を出すには：

1. **公開の git リポジトリ**を作り、
2. その中に **`generate_properties.py`**（ランダム種を 1 個受け取って問題を作るスクリプト）、
3. **`.onnx` ファイル群**のフォルダ、**`.vnnlib` ファイル群**のフォルダ、を置き、
4. GitHub の issues に「こういうお題です」とリンク付きで投稿する。

（`generate_properties.py` は **Python 3.8**、**t2.large** という AWS マシンで動く前提。）

**お題に票が集まると採点対象**になる：
- ツール参加者の **半数以上**が投票 → **Regular track**（本戦）。
- **1 票でも**入れば → **Extended track**（拡張戦）。
- 0 票 → 採点されないが、レポートには載る。

---

## ここが大事：私たちの提案は「ふつうのお題追加」では収まらない

今のルールは **「固定された AI 1 個を解く」前提**です（入力 = `.onnx` + `.vnnlib`、答え = 安全/危険）。

ところが私たちの `online-arch-evo` は **「AI を改築し続けながら、1 手ごとに安全かを差分チェックする」** もの。これは今の「1 問 = AI 1 個」という**問題の出し方（入出力の決まり）そのものに当てはまりません**。＝ これがまさに提案論文の「**契約不一致（contract mismatch）**」の論点です。

なので私たちの動きは：

- 「既存ルールにお題を 1 個足す」だけでは**ない**。
- **ルール議論の場（rules discussion の GitHub issue）で「新しいカテゴリ（新しい問題の出し方）」自体を提案・相談する**ことになる。
- 幸い、ルール変更は **動議（motion）→ 別チームが賛同（second）→ 過半数投票**というコミュニティ手続きが用意されていて、**提案は歓迎される**文化（誰でもお題提案可・上限なし・非ツール参加者も可、と明記されている）。
- さらに **Competition Contribution の short paper（4〜6 ページ、SAIV の論文集に収録）** という発表枠もあるので、将来エディションで「カテゴリ提案＋お題」を論文として出す道もある。

---

## まとめ（3 行）

1. これは「AI 安全性を**証明する道具**の腕くらべ」で、**お題提案者**としてなら**誰でも参加できる**。
2. 採点は「**間違いの罰がとても重い**」設計。お題は公開 git に `.onnx`＋`.vnnlib`＋種生成スクリプトを置いて出す。
3. 私たちの `online-arch-evo` は今の「固定 AI 1 個」の枠に収まらないので、**ルール議論で"新しい問題の出し方"を提案する**動きになる（コミュニティは提案歓迎）。
