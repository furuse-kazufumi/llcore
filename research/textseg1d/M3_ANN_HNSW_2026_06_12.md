# M3 ANN 化 (faiss HNSW) — recall 実測と「この規模では速くならない」の開示 (2026-06-12)

> ROADMAP M3 の残設計課題「ANN 化 (10 万 annotations 級で総当たり cosine が限界)」の
> 実装 + 実測。正本データ = `out/rad_ann_check.json`、スクリプト =
> `scripts/rad_ann_check.py`、実装 = `src/llcore/clip/annotations.py`
> (commit: ann_index + query(ann=True))。

## 背景 — 全量取込の前提条件

RAD 全量 = 49 分野 ~17.8k docs (実測 `D:/docs/*_corpus_v2/`)。M3 (i) の比率
(1,989 docs → 59,971 ann ≈ 30 ann/doc) を当てはめると **~50 万 annotations 級**。
総当たり cosine は行数に線形なので、この規模に進む前に近似最近傍 (ANN) の
配線と正しさの実測が必要 — それが本検証。

## 設計判断

- **faiss HNSW** (`IndexHNSWFlat`, M=32, efConstruction=80, METRIC_INNER_PRODUCT)。
  行は単位 L2 ノルム (store の不変条件) なので内積 = cosine。
- **optional extra `llcore[ann]`** (faiss-cpu>=1.8)。不在時は ImportError で
  **fail-closed — 黙って exact に劣化しない** (近似であることの明示が honest 要件)。
  基本機能は従来どおり stdlib + numpy で完結 (optional extras 設計の維持)。
- **`query(ann=True)` は opt-in**。既定は exact 総当たり (後方互換・結果不変)。
- **フィルタとの両立 = over-fetch**: domain/role/exclude_questions で間引かれても
  k 件を満たすまで候補幅を 4 倍ずつ広げて取り直す (全行に達したら打ち切り)。
- **`quantized=True` との併用は未定義のため fail-closed** (ValueError)。
- **index キャッシュは行数変化で全再構築**: HNSW は逐次 add 可能だが、構築
  パラメータの一貫性と実装の単純さを優先 (取込はバッチ前提の運用)。
- unit +4 = 403 PASS (faiss 不在環境は importorskip で除外)。

## 測定 — (iii) +800 と同一の 23k store、事前登録 40 probe

構成: 会話 35 turn + loop 39 docs + astro 800 docs = 23,169 annotations
(build 241s)。encoder = MiniLM。probe = loop 18 (WORLD_PROBES) + 会話 22 (PROBES)。
HNSW 構築 = **1.94s**。

| 測定 | exact | ann (HNSW) |
|---|---|---|
| recall@10 (40 probe 平均, ann が exact top-10 を再現) | — | **0.9825** (min 0.8) |
| top-10 順序完全一致 | — | 34/40 probe (85%) |
| query latency 平均 | 19.6ms | 16.9ms |
| loop 18 probe `domain="loop"` 併用 | MRR 0.6389 | **MRR 0.6389 (完全一致)** |

- **正しさ = 実用水準**: recall@10 平均 0.98。フィルタ併用 (over-fetch 経路) でも
  R@1/R@3/MRR が exact と全 metric 一致 — 配線は全量取込に進める品質。
- **取りこぼしの開示**: min 0.8 = 一部 probe で top-10 中 2 件を逃す。score は
  訪問ノードの厳密内積なので、入った候補の順序は正確 (一致 85% の不一致分は
  深い rank の取りこぼし起因)。

## 解釈 (honest)

1. **23k 規模では ANN は速くならない (19.6ms → 16.9ms = 誤差レベル)**。これは
   スクリプトの事前登録留保どおり。query latency の支配項は MiniLM の query
   encode (~15ms 級) であり、23k の総当たり cosine 自体が数 ms しかないため、
   そこを近似しても総時間は動かない。**本測定の価値は速度でなく、正しさ
   (recall) の実測開示と全量取込前の配線確認**にある。
2. **ANN が意味を持つ分岐点は ~10 万行超**: 総当たりは行数線形なので 50 万行で
   ~100ms 超 → encode を上回り支配項が逆転する。HNSW 構築 1.94s @ 23k から
   外挿して 50 万行でも構築 ~1 分級 = 許容範囲。
3. **限界 (未解決のまま開示)**:
   - recall < 1.0 は HNSW の本質 (efSearch を上げれば recall↑ / latency↑)。
     現値 efSearch = max(2×候補幅, 64) は 23k での実測値 — 50 万行で再測が必要。
   - 全再構築キャッシュは逐次取込に不向き (バッチ取込前提)。
   - int8 (quantized) との併用は未定義のまま fail-closed — 必要になったら設計。
